# CivilSolve Agent Notes

CivilSolve is a civil engineering assignment solver hosted on a single Cloudflare Worker (free tier). Read `README.md` before editing.

## Core Invariants

- **Keep API keys server-side only.** Keys live in `.dev.vars` locally and in Wrangler secrets in production. Never expose one to frontend code, and never put one in a URL or query string (Google auth uses the `x-goog-api-key` header for exactly this reason).
- **Providers and channels are separate concepts.** A provider is a UI choice (`chatgpt`, `claude`, `gemini`, `deepseek`, `grok`, `mimo`, `muse`); a channel is the upstream account (`poe`, `opencode`, `google`). Routing lives in `ROUTES` in `worker/channels.ts` — add channels there, not by branching in `worker/run.ts`.
- **Thinking effort is mapped per route, never passed through.** The five UI levels do not exist on every model: OpenAI-style enums take `none`/`xhigh` only on GPT-5.x, Claude has no "off" value, Gemini takes an integer token budget and Pro-tier models cannot disable thinking. A level with no mapping sends nothing.
- **Only visible output becomes a `delta`.** Reasoning summaries (`response.reasoning_summary_text.delta`, `reasoning_content`, Gemini parts flagged `thought: true`) must never be concatenated into the answer — they corrupt the JSON the parser expects, and they get more frequent at higher effort.
- **Model output is untrusted.** Uploaded images are user-supplied, so anything in them can steer what a model writes. Anything rendered through `dangerouslySetInnerHTML` must pass DOMPurify first (`src/lib/math-markdown.ts`).
- **Keep `/api/solve/:provider` streaming.** The Worker sends SSE headers immediately and heartbeats every 15s — that is what lets minutes-long provider calls survive on Workers without any job storage. Do not convert it to a buffered request/response.
- **No server-side storage.** The app is intentionally stateless: no KV, D1, R2, or Durable Objects. Uploads are converted to data URLs in the browser and never persisted. This is also why each provider re-uploads the same images: deduplicating would require storage or a single fan-out request, and both are ruled out.
- **Enforce request limits on real bytes.** `content-length` is a claim, not a fact — a chunked request has none. `readBoundedBody` in `worker/index.ts` counts what actually arrives and abandons the request at the cap, before the JSON parser sees it. Parsing the body is the single largest CPU cost in an invocation; keep it bounded.
- **Provider failures are per-provider.** A Claude failure must not hide the others — each tab has its own run state.
- **Keep math rendering in the web UI.** Users read formulas via KaTeX directly; PDF export is a browser-print convenience, not a requirement for reading solutions.
- **Keep katex/marked/dompurify out of the initial bundle.** They are only imported by `src/lib/math-markdown.ts`, which is only reachable through the lazily loaded solution panel. Do not import them (or that module) from eagerly loaded code.
- **`shared/` is pure string logic** shared by the Worker and the client. No DOM, no Workers APIs, no imports from `src/` or `worker/`.
- Accepted uploads: JPEG, PNG, WebP, GIF, PDF only. HEIC/TIFF cannot be canvas-decoded in browsers; iOS auto-converts HEIC on the picker.
- Every model **must be vision-capable** — the assignment is sent as images, never as OCR text. Verify with an image before changing any model id; text-only models often answer anyway, and some say "I cannot view the image" and then invent a plausible solution, which is far worse than an error.

## Failure handling

`worker/run.ts` distinguishes five failure modes; keep them distinct:

1. **Parameter rejection** (400/422 naming `reasoning`, a schema field, or a generic parameter error) → step down the capability ladder: drop `reasoning`, then relax strict JSON schema to plain JSON mode, then drop the schema. Reported to the client as a `status` event. No sleep, does not consume the retry budget.
2. **Transient failure** (408/409/429/5xx, or a failure that never reached a response) → one retry after 3s. **If the route has a model chain** (a comma-separated model var, e.g. `gemini-3.8-flash,gemini-3.5-flash`), the retry switches to the next model first, after the same 3 s pause, and the new model gets a fresh transient budget; only when the chain is spent does the same model get retried. Modes 4 and the fragment case in 3 switch models the same way. A different model is more likely to fix "did not answer" than asking the same one again.
3. **Thinking exhaustion** (the model spent its whole output allowance on reasoning and wrote no answer) → retry once, one effort level down. Repeating the request unchanged would repeat the outcome, so this sheds thinking instead. The step-down deliberately goes below the route's `minEffort`: the floor chooses where a solve *starts*, not what it must fail at. Detected by `isThinkingExhausted` — responses `status: "incomplete"` + `incomplete_details.reason: "max_output_tokens"`, chat-completions `finish_reason: "length"` — always with the guard that no usable content arrived, so a truncated answer is still delivered rather than retried. Capped at one because the wasted attempt runs to its full budget (~120 s measured) and a second would risk the 280 s safety timeout. A level with nothing below it (`none` on a clamped route) reports the clear message and stops.
4. **Dropped connection** (the stream ends with no terminal frame — no `[DONE]`, no `finish_reason`, no `response.completed` — and nothing accumulated) → same as a transient: one retry after 3s **at the same effort**. Tracked by `isTerminalFrame` per dialect. Measured on OpenCode Go: 20,725 characters of reasoning streamed over 128 s, then the connection closed mid-word. This is deliberately *not* the effort step-down: nothing says the effort was the problem. Before this was distinguished, it surfaced as the same "returned an empty response" as exhaustion did.
5. **Everything else** (401, 404, an `error` object inside an HTTP 200 body) → fail immediately. Retrying an auth error only delays the message the user needs.

Never retry the safety-timeout abort. Never retry after a `delta` has reached the client, **with one deliberate exception**: a stream that ended early *with* answer text (dropped with no terminal, or `finish_reason: "length"` / `incomplete_details.reason: "max_output_tokens"` after some output). `fetchStreamed` attaches the text to the error as `partialText`; `runTask` hands it to the task's `finalize` with `lastAttempt` set from the remaining budget. A prefix that reaches `final_answer` is delivered as a truncated answer. One that does not is worth nothing, and the user has already paid the wait, so it is retried — at the same effort for a drop, one level down for a cap — and only on the last attempt does the parser accept it as working-plus-note. The client resets its character count on any `status`, so a retry reads as a restart, not as the count continuing from discarded text. Measured on Grok: a stream that stopped 676 characters into the answer, which the parser rightly refused and which surfaced as "invalid JSON" until this existed.

A stream request does not guarantee a stream back: a gateway may answer an invalid request with HTTP 200 and a plain JSON body, or ignore `stream: true`. `fetchStreamed` in `worker/run.ts` checks the content type and parses a non-stream body as a payload; do not assume `response.ok` plus an event-stream content type.

**When a stream drops after partial content**, what arrived is a valid prefix of the solution JSON. `recoverTruncatedJson` in `shared/solution.ts` closes the open string and the object, keeps every complete field, marks the cut one, drops a cut `latex_body` so the fallback rebuilds it, and — only when `allowIncomplete` is set, i.e. on the last attempt — says so when the cut landed before `final_answer`; with attempts left that case is rejected so the caller retries instead. The prose synthesizer refuses text that is plainly a schema attempt, so an unsalvageable blob reports invalid JSON instead of a "solution" whose final answer is a stray `"latex_body": …` fragment — which is what one Qwen run produced before this existed. Verified through the real `/api/solve` path against seven cut points (inside the LaTeX, inside `step_by_step`, inside `final_answer`, inside a key name, after a dangling key, inside a `\u` escape, between tokens).

## History

- **Kimi, MiniMax and Qwen were removed in September 2026**, along with the Kimi Code / Moonshot / MiniMax channels and the Anthropic-protocol dialect that only they used. The evidence is the B.8 matrix below: across two full runs (36 cells) Kimi was 0/4, Qwen 0/8 and MiniMax 1/4. Everything learned about them — Kimi Code rejecting forced tools while thinking, `api.kimi.com` returning a 403 challenge page to Workers' egress, MiniMax honouring a forced tool only while thinking is on and wrapping results in the schema name, `kimi-k2.7-code` misreading a 4 m UDL as 6 m at effort `low`, MiniMax M3 thinking itself out of `max_tokens` at a 16384 budget and returning a confidently wrong answer when given 90112 — is in git history (the `ROUTES` entries, `ANTHROPIC_BUDGET`, `toAnthropicImage`, the `base_resp` check, and the corresponding notes here, all before commit `df91701`). Two mechanisms they motivated stay because they are general: the `structured: false` route flag with the prompt-carried shape contract, and the effort step-down in failure mode 3.
- The repo previously carried a second, unused backend from the original Bun/Zo deployment (`server.ts`, `backend-lib/`, root `index.tsx`, `zosite.json`). It was outside both tsconfig `include` globs, so `npm run check` never covered it. It has been removed — recover it from git history if you need to consult the old provider logic. Everything that ships now lives in `worker/`, `shared/`, and `src/`, and all three are typechecked.

- **The interpretation pass is opt-in.** `/api/interpret` costs three extra model calls before the first solution appears, so it stays off unless the user ticks it. Do not make it the default.
- **The answer cross-check is opt-in, and the judge is blind.** `/api/judge` grades the ticked solvers' solutions (two to four) against the images; the browser labels them Solution A, B, C, D in picker order and never sends provider names, so the judge grades the work rather than the brand (the verdict card maps the letters back). The prompt makes the judge re-derive the numbers: the wrong answers seen on the fixtures were all internally consistent, so a consistency read would pass them. Off by default - one extra call - and the judge (ChatGPT by default) runs at `high`, the most reliable level in the B.8 matrix, not the top one.
- **`worker/run.ts` is task-agnostic.** Solve, interpret and judge differ only in prompt, schema, and `finalize`. Add new model-calling features as another `Task`, not another orchestrator.

## CPU budget

**The account is on Workers Paid since 22 September 2026** (30 s of CPU per invocation by default, `limits.cpu_ms` up to 5 min). Measured on production that day, all `outcome=ok`: MiMo streamed B.8 1,424 ms; DeepSeek streamed B.8 3,201 ms (77 s; the free plan had killed the same solve at 63 s); DeepSeek as interpretation judge 1,906 ms; the Gemini and Muse Spark readers 18 and 46 ms. `NO_STREAM` is cleared. The paid plan changes nothing about correctness — MiMo still answered −38/+4 and DeepSeek −460 on that run — it only removes the `exceededCpu` kills. Everything below was measured on the free plan and stays as the record of why the code is shaped as it is (single-choice picker, sequential interpretation pass, `NO_STREAM`) and what to re-enable if the account ever drops back.

Measured with `wrangler tail` (`cpuTime` per request), September 2026. Re-measure before drawing new conclusions; do not reason from Node timings, which are 40-100x lower than workerd's for the same stream.

- **Cost is per upstream chunk read, in the runtime, not in our JS.** A thinking model on OpenCode Go sends one HTTP chunk per token; workerd hands them over at ~57 bytes per `read()` and charges roughly 70 us each. One 47 s solve on a per-token route is ~7,400 reads. That is why CPU tracks streaming *duration* (~8-30 ms per second) and why cutting client writes 26x (1113 -> 43) and skipping JSON.parse on reasoning frames left CPU unchanged (410-1378 ms before, 531 ms after, same fixture).
- **Reads cannot be coalesced from JS.** A BYOB reader with a 64 KB buffer plus a 100 ms pause before each read still averaged 57 B/read; workerd does not queue between reads. That experiment was measured and discarded - do not repeat it.
- **Non-streamed upstream IS the escape for a model that streams its reasoning — within the idle cut.** opencode.ai closes a request that produces no bytes for ~100-120 s, so `NO_STREAM` only fits a model whose whole solve lands under that. `deepseek-v4.1-flash` does on both fixtures (B.8 at `medium` 85–87 s, the beam 41–47 s), and the difference is decisive: streamed, its B.8 solve was **killed at 2,010 ms of CPU** (`outcome=exceededCpu`, 63 s in, zero answer deltas — the kill lands during reasoning, which `chat-completions` streams token by token as `reasoning_content`); non-streamed, the same solve completed for **13 ms**, the beam for 9 ms. `NO_STREAM=deepseek` was set in production on 21 September 2026 and cleared the next day when the account moved to Workers Paid (the streamed solve then completed for 3,201 ms). A hard problem that runs past the idle cut will fail at the gateway instead — still better than a certain CPU kill, and the client's retry gets a second chance. The same trap should be assumed for any other `chat-completions` thinking model (MiMo streams `reasoning_content` too; unmeasured on production).
- **Why ChatGPT survives the free plan and DeepSeek did not:** the `responses` API on OpenCode Go does not stream gpt-5.6-luna's reasoning at all — a 116 s solve sent one `ping` and then the answer — so its chunk count is small. `chat-completions` streams every reasoning token. Same gateway, same plan, opposite CPU profiles; check which dialect a route speaks before assuming its CPU cost.
- **Where the CPU goes, per provider, one easy solve:** Poe routes 22-48 ms (Poe buffers upstream, few chunks); Google ~7-10 ms (buffers hardest); OpenCode Go streamed routes 330-500 ms on the easy fixture and ~2,000 ms on B.8 (per-token). The chunk count is set by the sender: a direct measurement of the same fixture showed OpenCode Go's median chunk at 54 B against Poe's 177 B and Google's 435 B.
- **The free plan's limit behaves like a refilling budget, not a fixed 10 ms.** Rested single requests of 1378 ms passed; a 192 ms request right after several heavy ones was killed (`outcome=exceededCpu`). A kill is hard: no `error` event is written, the client sees the stream end and shows "ended unexpectedly, please try again". Rapid-fire testing drains the budget far faster than real use does - space test runs out by minutes.
- **The local dev server drops an idle upstream stream at ~60 s; production does not.** Through `npm run dev`, a Muse Spark solve at `high` or `medium` failed twice in a row at 62-63 s with workerd's `Network connection lost.` (the responses dialect streams nothing while the model thinks); the same solve on production completed in 117 s with no retry, correct. The earlier "socket resets at 4-63 s" seen on Muse were this. Measure connection reliability on production, never locally.
- **What this means for users:** one solve at a time, minutes apart, works. Back-to-back solves, the interpretation pass (three extra calls) on top of a solve, or several users at once will get some tabs killed. Workers Paid ($5/month, 30 s CPU per invocation by default) removes exactly this class of failure and nothing else: every failure in the B.8 matrix below happened on a local worker with no CPU limit at all. The owner upgraded on 22 September 2026. Before that the remaining levers were all product choices: lower thinking on the OpenCode routes, or accepting retries.

## Provider gotchas found by testing

- **OpenCode Go needs `x-opencode-session` on every request.** Without it the gateway returns `MissingSessionID` even though `GET /models` works, so a valid key can look broken. The Worker sends a UUID per solve.
- **OpenCode Go fixes the protocol per model** — Responses for GPT Luna, Grok and Muse Spark; chat completions for DeepSeek and MiMo. Which models accept images is not documented reliably: `deepseek-v4-flash-vision-exp` is the one DeepSeek model it documents as vision, but `deepseek-v4.1-flash` and `deepseek-flash` read the B.8 diagram too (all six values, ~5 s), so probe rather than trust the docs.
- **The China-hosted-models opt-in unlocks `deepseek-v4-pro`, and it is text-only.** With the opt-in off it 403s; with it on it accepts the image part and answers "I can't read the image because it is unsupported" — the exact failure the vision invariant exists to catch, though at least this one admits it rather than inventing a solution. `deepseek-v4-flash` is text-only too and rejects image parts outright (400). Neither is a route. The opt-in was turned on 20 September 2026; whether `deepseek-v4.1-flash` depends on it is untested, so if DeepSeek starts 403-ing, check that toggle first.
- **`longcat-2.0`, `hy3`, `hy4-preview` cannot see images** (LongCat replies "NO IMAGE"; Hy rejects image parts). `deepseek-v4-pro` and `muse-spark-*` need a workspace opt-in before the key can call them.
- **OpenCode Zen's documented free-tier ids are not the Go gateway's ids.** The docs list `mimo-v2.5-free` and `muse-spark-1.3-contributor-free`; the Go gateway answers "Model … is not supported" to both and serves the same tiers as `mimo-v2.5` (the paid sibling is `mimo-v2.5-pro`) and `muse-spark-1.3-contributor`. Trust `GET /models` over the docs page.
- **There are two OpenCode gateways behind one key, and only Go is usable here.** `https://opencode.ai/zen/v1` (Zen, 74 models) and `https://opencode.ai/zen/go/v1` (Go, 37 models) both accept the same `OPENCODE_API_KEY`, with different catalogues and ids. Zen is pay-as-you-go: its paid tiers (`muse-spark-1.3` at $1.25/$4.25 per 1M) answer `401 CreditsError: Insufficient balance` with a billing link when the balance is zero, and the owner does not want per-call billing. Its *free* tiers (`muse-spark-1.3-contributor-free`) answer `403 FreeTierError: OpenCode's free tier can only be used from within OpenCode` — they are locked to the OpenCode app and CLI and cannot be reached from any third-party API client, credit or no credit. So a "use Zen's free quota first, fall back to Go" design is impossible; the only API-reachable Muse Spark is the Go contributor tier, on the Go subscription quota. A `zen` channel was built and reverted the same day; nothing here uses that gateway.
- **`muse-spark-1.3-contributor` is behind a data-policy opt-in.** With no opt-in the gateway returns `403 DataPolicyError: This model collects data used to improve its quality and requires explicit opt in: https://opencode.ai/workspace/<id>/go`. The workspace opted in on 20 September 2026; a fresh workspace will see the 403 as the provider's error message until it does the same. After the opt-in it reads the B.8 diagram (all six values, 8.6 s) **and solves it**: correct at `none` (100 s), `low` (48 s — the fastest correct B.8 solve from any provider) and `medium` (127 s); `high` died to two consecutive connection drops. The simple beam was right at `none` and `medium`. That is 5/6, and 3/3 on the hard problem where it finished — better than the paid DeepSeek and Grok, level with ChatGPT@high, for nothing. The cost is reliability of the *connection*, not the model: five of six runs needed the transient retry (socket resets at 4–63 s), which is the worst rate seen on OpenCode Go; the retry caught four of them. Prefer `low` here — it was both correct and quickest.
- **`mimo-v2.5` reads diagrams, solves routine problems, and fails the hard one.** Asked for the values shown in the B.8 image it returned all six (60 mm, 35 mm, 10 m/s, 100 kPa, 30°, 0.5 kN) in 6.5 s. On the simple beam fixture (6 m simply supported, 10 kN/m UDL + 20 kN at 2 m; RA = 43.33 kN, RB = 36.67 kN, Mmax = 67.22 kNm at 2.33 m) it was right at `none` (37 s) and `medium` (92 s). On B.8 it was 0/4: `none`, `low` and `medium` gave the −38 N / +4 N continuity misread, `high` got Fx right and Fy wrong (317 N). It is kept because it is free and correct on routine work; do not reach for it on a problem that needs the velocity of an unstated jet derived from continuity. Two of six runs needed the transient retry (socket reset at 58 s and 87 s) — OpenCode Go's connection instability, not MiMo's.
- **`gpt-5.6-luna` accepts `reasoning.effort: "xhigh"`.** The ChatGPT route floors at `high` (`minEffort`), so the user chooses between `high` and `max`; on the hard fixture `max` was the fastest of the set at 13.7 s, so top thinking does not cost latency there.
- **Poe bot handles drift.** `GPT-5.6-Terra` and `Claude-Opus-5` do not exist; list what a key can see with `GET https://api.poe.com/v1/models`. Newer Gemini handles there (`gemini-3.8-flash`) answer "Model does not support responses method" — the Poe route uses the Responses API, so only bots mapped to it work.
- **The Google key is free-tier, and that decides the model.** `GET /v1beta/models` lists everything, but `generateContent` on `gemini-3.1-pro-preview` answers `429 RESOURCE_EXHAUSTED` (Pro has no free quota) while every Flash model answers. The previous key's whole project was `403 PERMISSION_DENIED` on every call, model listing included — a denied project and an exhausted quota look nothing alike, so check which one you have before changing ids. Free-tier rate limits apply; the tests here were spaced 8–10 s apart.
- **Google buffers upstream harder than Poe.** Measured chunk granularity on the same fixture: Google median 435 B (98 chunks), Poe 177 B, OpenCode Go 54 B. At ~70 us per read that is ~7 ms of CPU per solve on the free Workers plan — the cheapest route there is, which is why Gemini reads on Google for the interpretation pass.
- **`gemini-3.8-flash` is the best reader when it answers, and it often does not.** Six interpretation runs on the B.8 image (a 190 KB request): it closed the TLS socket after accepting the body, with zero bytes back, four times — reproduced from a cold Node client as `SocketError: other side closed`, so it is Google's backend, not workerd — and once returned a "successful" reading with empty `given` and `required`. The 35 KB beam request went through fine, so it looks payload-related. `gemini-3.5-flash` behind it in the chain was 4/4 with full readings in 18–25 s, and 3/3 on solves (B.8 at `low` in 33 s). `gemini-3.7-flash` answered 503 on the quota probe. The chain is 3.8-first by the owner's choice; flip the order in `INTERPRET_GEMINI_MODEL` if 3.8's failure rate stays where it is.
- **A completed response the parser rejects now moves down the chain too.** The first production reader call after the Google secret went in came back from 3.8-flash as a "successful" 313-character JSON fragment, which `parseInterpretation` accepted as prose and delivered with four empty fields. `finalize` is now called inside the retry loop: a rejected result switches model if the chain has one left, and only on the last attempt does the parser accept prose or a reading with neither `given` nor `required` (`allowIncomplete`, the same gate `parseStructuredSolution` has). Verified against a fake that completes with a fragment on 3.8, and then on production: three reader calls, each 3.8 → 503 → 3.5 → full reading in 12–23 s.
- **Local dev cannot exercise the fallback against Google.** In `npm run dev` (miniflare), a request to `generativelanguage.googleapis.com` that follows a failed one to the same host fails with `internal error; reference = <id>` — every time, pause or no pause — while the identical request from a cold Node client and from production workerd succeeds. It is the local runtime's connection handling after an upstream error, not Google and not the worker code. Prove chain behaviour with a fake upstream locally and with real calls on production; do not read local `internal error` as a Google failure.
- **Claude on Poe rejects the reasoning parameter**, and the downgrade ladder catches it. Do not "fix" this by removing the parameter for everyone — GPT-5.x accepts it.
- **DeepSeek rejects the strict JSON schema** on every run — both models — and the ladder relaxes it; this costs nothing and is expected. The family shares one failure: double-counting the pressure term on B.8 (Fy = -460 N for -177.5 N). `deepseek-v4-flash-vision-exp` did it at `low` once and at `high` twice (5/8 overall; right every time at `none` and `medium`). `deepseek-v4.1-flash`, the default since 20 September 2026, did it once at `none` and was right at `low` (twice), `medium` and `high` (4/5), plus 2/2 on the simple beam. Solve times are similar (79–125 s on B.8) despite 4.1-flash answering a short read-only question in 5 s where -vision-exp took 36 s and 6,844 tokens; both think hard on a real solve. Small samples, same weakness, modest edge — revert with one var if it regresses.
- **The OpenCode Go routes can think themselves out of tokens, and it was invisible until September 2026.** The worker sends no output-token cap on the `responses` or `chat-completions` dialects, so the gateway's own default is the ceiling. A gpt-5.6-luna run that *succeeded* used 16,343 output tokens (11,912 reasoning) — 41 short of 16,384 — so any run that thinks slightly harder is cut mid-reasoning with no message item. Forcing a small cap reproduces it exactly: `response.incomplete`, `incomplete_details.reason: "max_output_tokens"`, every output token spent on reasoning, zero answer. Before `isThinkingExhausted` covered these dialects, `extractCompleted` only matched `response.completed` and `extractPayloadError` only matched `response.failed`, so this surfaced as the useless "returned an empty response" — 6 of 18 cells in the first B.8 matrix. Do not "fix" it by sending a large explicit cap without measuring: on the since-removed MiniMax route the same idea produced a confidently wrong answer.
- **"Returned an empty response" was hiding two different failures.** Re-running the empty cells after the exhaustion detector was extended, one provider still came back with the *old* message — its stream carried no terminal frame at all. A direct dump showed the connection closing mid-word after 128 s of reasoning, `finish_reason: null`, no `[DONE]`. That is failure mode 4 (dropped connection, same-effort retry), not mode 3. Do not assume an empty stream means the model ran out of tokens.
- **B.8 matrix, every non-Poe provider × every distinct effort, two runs in September 2026** (correct: Fx = -142.9 N, Fy = -177.5 N; through the local worker, i.e. with no CPU limit). Before the fixes: ChatGPT high ✓ 59 s, max empty; DeepSeek none ✓, low ✗ (-460), medium ✓, high ✗ (-460); Grok none empty, low ✓ 29 s, medium ✓, high empty; Kimi 0/2, MiniMax 1/2, Qwen 0/4. After the fixes: ChatGPT high ✓, max ✓; DeepSeek none ✓, low ✓, medium ✓, high ✗ (-460); Grok none ✓, low ✗ (-38/+4), medium ✓, high 280 s timeout; Kimi 0/2, MiniMax 0/2, Qwen 0/4. Three lessons: **the top effort of every provider is the least reliable**; the default (ChatGPT at `high`) is the most reliable cell, 2/2; and run-to-run variance dominates — Grok@low was right in one run and wrong in the next, so never conclude a level is safe from one cell. The `-38 N / +4 N` answer is a reading error, not arithmetic — it assumes the second jet is also 10 m/s instead of deriving 19.4 m/s from continuity — and four different models produced it; the interpretation pass exists for exactly this.

These were all discovered by running real requests, not from vendor docs. Re-verify before changing a model id or a route flag.

## Verification

```bash
npm run check    # tsc --noEmit for SPA + worker
npm run build    # production build
npm run dev      # Vite + workerd locally; test /api/health and the UI
```

`GET /api/health` reports each provider's channel, model, and whether its key is configured — check it first when a provider tab errors.

For API testing use `curl -N` against the dev server (see README). Deployment is `npm run deploy` (requires `wrangler login` and at least one key secret).
