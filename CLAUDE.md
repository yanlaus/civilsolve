# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Read first

`AGENTS.md` holds the project invariants (keys server-side, providers vs channels, routing defaults in code once, effort mapping, untrusted model output, answers-only storage for 24 hours, CPU budget - the account is on Workers Paid since 22 September 2026, and the free-plan findings explain the code's shape), the five failure modes, and the provider gotchas found by real testing. `README.md` holds the full architecture, API, and config reference. Both are authoritative; this file only adds what is not already written there. Keep all three in sync when architecture, provider behaviour, deployment, or error handling changes.

## Commands

```bash
npm run dev        # Vite + Worker in workerd (localhost:5173), HMR, reads .dev.vars
npm run check      # tsc --noEmit for the SPA (tsconfig.json) AND the worker (worker/tsconfig.json)
npm run build      # vite build -> dist/client + worker bundle
npm run preview    # serve the production build
npm run deploy     # vite build && wrangler deploy (needs `npx wrangler login` + secrets)
npm run test:models  # node --test: routing, variants, presets and defaults (tests/model-variants.test.mjs)
npm run test:jobs    # node --test: TaskJob alarm dispatch, Stop, retention, local workerd
```

npm is the only package manager: `package-lock.json` is the one lockfile, and `.npmrc` sets `min-release-age=3` (no version younger than three days gets installed). Do not add another lockfile.

`vite.config.ts` takes its port from `PORT` when it is set (the desktop app's preview assigns one when 5173 is taken - `autoPort` in `.claude/launch.json`); otherwise it is 5173.

There is no linter. `npm run check` and the two `node --test` suites above are the automated verification; the model suite pins the presets and defaults, so a change to a preset, a default model or a variant list changes it too. Both tsconfigs must pass — `shared/` is included by both, so a change there is typechecked under DOM libs (SPA) and under Workers types (worker). To typecheck just one side: `npx tsc --noEmit` or `npx tsc --noEmit -p worker`.

Manual verification against the dev server:

```bash
curl http://localhost:5173/api/health
```

```bash
curl -N -X POST http://localhost:5173/api/solve/claude -H "content-type: application/json" -d '{"images":["data:image/jpeg;base64,..."],"notes":"","effort":"low"}'
```

Local secrets go in `.dev.vars` (copy from `.dev.vars.example`); they are read by the Worker via `c.env`, never by Vite. Any var in `WorkerEnv` (`worker/channels.ts`) can be set there to override a default for local runs. `wrangler.jsonc` `vars` is empty on purpose: the production routing is the code defaults (`DEFAULT_CHANNELS`, `ROUTES`, `INTERPRET_MODEL_DEFAULT`).

## Architecture in one pass

One Cloudflare Worker serves the Vite SPA as static assets and a Hono app for `/api/*` (`run_worker_first`). Everything streams over SSE, and every task runs in a `TaskJob` Durable Object of its own, which stores only its final answer, for 24 hours.

### Request path (worker)

`worker/index.ts` → `worker/run.ts` → `worker/channels.ts`

- **`index.ts`** first applies the `TASK_LIMITER` rate limit to the six task routes (per client IP, 429 past it; there is no sign-in - Cloudflare Access sign-in is parked on the `access-sign-in` branch, see `AGENTS.md`). Then it validates the body (`readBoundedBody` counts real bytes against `MAX_BODY_BYTES`), builds the task with `buildTask` (`worker/tasks.ts`) so a bad request gets its 400 at once, then hands the raw body to a fresh **`TaskJob`** Durable Object (`worker/jobs.ts`) - near the user, or at the route's `region` when it has one - and returns its stream. A task is `{ prompt(fn), instructions, schemaName, schema, images, referenceImages?, session }` plus a `finalize(rawText)` callback; it carries functions, so the job rebuilds it from the body with the same `buildTask`. `/api/solve`, `/api/interpret`, `/api/judge`, `/api/study`, `/api/ask` and `/api/align` differ *only* in the task `buildTask` makes. `GET /api/jobs/:id` re-attaches to a job, `DELETE /api/jobs/:id` cancels one, and `GET /api/pdf/:id` prints a finished solution, verified answer or study notes to PDF with Browser Rendering and keeps it for good in R2 (`worker/pdf.ts`; served from the edge cache or R2 when it can be; capped by `PdfBudget` and `PDF_LIMITER` - see `AGENTS.md`). A new model-calling feature is a new task kind, not a new orchestrator.
- **`jobs.ts`** - `TaskJob` runs `runTask` into a hub sink that never rejects, so the run outlives the page; the stream opens with `event: job {id, startedAt, deadlineAt, now}` (the deadline from `taskTimeoutFor` in `run.ts`); `status` / `done` / `error` are stamped with `at`, and a re-attach replays every status so far (memory only); the final event is stored and an alarm deletes it 24 h later. Images are never stored. Muse and ChatGPT on OpenCode use `startInAlarm`: the HTTP handler opens SSE and schedules the platform alarm, which consumes the in-memory task once and awaits `runTask`. `expiresAt` distinguishes dispatch redelivery from retention cleanup. Stop works while queued or active; resets never replay input from storage.
- **`run.ts`** is dialect- and task-agnostic and writes to a `TaskSink` (the job's hub, or `streamSink` on the inline fallback path): immediate SSE headers, 15 s heartbeats, a safety timeout that is a 280 s floor (a route may raise it with `timeoutMs`; MiniMax, DeepSeek, MiMo, Kimi, Gemini, ChatGPT, Qwen and GLM use 20 minutes) plus 2 min per assignment page after the first, capped at 45 min (14 min for alarm routes, including dispatch wait, below the platform's 15-minute alarm wall limit) - `taskTimeoutMs` in `shared/stream-protocol.ts`, delta coalescing (2048 chars / 400 ms), and the retry/downgrade loop. `Capabilities = { reasoning: bool, schema: "strict" | "loose" | "none" }` degrade independently when an upstream 400/422 names a parameter (`paramRejection`); a 400/422 whose body carries no error message (`isSilentRejection`) is read as a schema rejection - DeepSeek's gateway refuses strict schemas that way; transient statuses and dropped streams get one retry after 3 s at the same effort, as does OpenCode Go's relayed `server_error` 400 "Upstream request failed: Invalid request parameters" (`isRelayedUpstreamFailure`, on a fresh `x-opencode-session`, before `paramRejection` may read it as a refused parameter - Kimi K3, 15 October 2026); thinking exhaustion gets one retry one effort level down; nothing is retried once a `delta` has reached the client, except a stream that ended early with a fragment `finalize` rejects, and a completed response `finalize` rejects (a blank template, an empty object), which gets one retry (see failure handling in `AGENTS.md`). The timeout's `error` carries `timedOut: true`.
- **`channels.ts`** owns the `ROUTES` table (`Record<ProviderKey, Partial<Record<ChannelKey, RouteSpec>>>`), `resolveRoute(provider, env, override?)`, and per-**dialect** request building + stream parsing for the four dialects: `responses`, `chat-completions`, `gemini`, and `messages` (Anthropic Messages, since 10 October 2026 - Claude Haiku on OpenCode Go speaks nothing else). A `RouteSpec` carries `effort: EffortSpec` (enum or token budget, per level — a missing level sends nothing), optional `startSchema` (the rung to start on - DeepSeek and Kimi start at `"loose"`: DeepSeek's gateway refuses strict schemas, and Kimi answers one with `{}`), optional `region` (a Durable Object location hint `handleTask` creates the route's job with, for a model served in some countries only - Muse Spark's and, since 18 October 2026, ChatGPT's on OpenCode is `"wnam"`, so ChatGPT is called exactly the way Muse is - Muse's since its contributor tier answered students abroad with 403 "not available in your country"; it did not stop the 403 for a student in Hong Kong - under HTTP invocation, Cloudflare passes the visitor's country on to the job's subrequests wherever the job runs - so `isRegionRefusal` in `run.ts` reports such a refusal plainly instead - see `AGENTS.md`), `startInAlarm` (Muse/OpenCode since 11 October 2026, at the owner's request; metadata measured differently in alarm context, see `AGENTS.md`), `forceEffort` / `minEffort` / `maxEffort` (`clampEffort` in `run.ts` applies the band; the form disables the levels outside it), and `streaming` / `structured` flags that record what the upstream can actually do (`structured: false` puts the field contract in the prompt; the strict schema is still sent until the ladder drops it). `DEFAULT_CHANNELS` is each provider's channel list when its `*_CHANNEL` var is unset. A channel list may be a chain (MiniMax's default, `minimax,opencode`, and Gemini's, `google,google-backup`): `resolveRoute` picks the first channel whose key is set and keeps the rest as `fallbackChannels`, and `switchChannel` in `run.ts` moves down it on an account refusal (plan ended, credit gone, key revoked) or after a channel's transient retry. A route pinned to one channel (an override) still gets that channel's `BACKUP_CHANNELS` - accounts that name the same models alike (Gemini's Vertex key → its backup key) - and keeps its pinned model when it moves, so Gemini's Pro pick and the Gemini reader fall back too. `interpretOverride` is how `/api/interpret` pins ChatGPT (Luna on OpenCode Go), Gemini (Google chain) and Claude (Opus on Poe) to routes chosen for the pass, regardless of the solve-time channel.

Adding a channel = one entry in `ROUTES` plus its env vars in `WorkerEnv` (and `DEFAULT_CHANNELS` if it becomes the default); nothing goes in `wrangler.jsonc` unless production must override a default. Adding a dialect = extending `buildRequest`, `extractDelta`, `extractFinalText`, `extractPayloadError`, `streamTerminator`, `isReasoningOnlyFrame`, `isTerminalFrame`, `isThinkingExhausted`.

Pure string logic compiled into both bundles — no DOM, no Workers APIs, no imports from `src/` or `worker/`.

### Client (`src/`)

- `hooks/use-solve.ts` — per-provider state machine (`idle → waiting → streaming → done | error`) over `lib/sse.ts`. Every ticked provider runs through `runPool(…, SOLVE_CONCURRENCY, …)` at once — 4, the most the cross-check can grade (it was 1 on the free plan; see the CPU section of `AGENTS.md`). A lost connection - a network `TypeError` such as Safari's "Load failed" when a phone backgrounds the browser, or a stream that closes with no terminal event - is resumed per provider by `withResume` (`lib/sse.ts`): it waits until the page is visible and online, then `openTaskStream` re-attaches to the same job by the id its `job` event carried (a `JobHandle`), backing off up to 15 s between tries and giving up only after `RECONNECT_WINDOW_MS` (2 minutes) without a reconnection getting through; it starts over, at most once (`MAX_RESTARTS`), only if the server no longer has the job. A read that gets no byte for `STREAM_IDLE_MS` (45 s; heartbeats come every 15 s) counts as a lost connection too - a phone's half-open socket otherwise spins forever. Each solver and the judge keep a `Progress` timeline (`lib/progress.ts`: start, deadline, end, every status with its time, on the page's clock via the job's `now`), which `solution-panel.tsx` shows as a running clock and a status log (the timeout is deliberately not shown); a timed-out task is orange. Job ids are saved in localStorage (`lib/run-store.ts`), so `restore()` recovers the last run after a reload; `cancel()` (Stop all) sends `DELETE /api/jobs/:id` for every job, and `stopProvider` / `stopJudge` stop one task, on its own `childController` (`stopTask` in `lib/sse.ts`; a Stop before the job's id is known is sent once `takeJobEvent` sees it). A stopped task is an `error` with `stopped: true`, grey in the panel. `refineProvider(provider, instructions)` and `refineVerdict(instructions)` re-generate a finished solution or verdict with the user's instructions (`revision` in the body: the last version as text plus the instructions); the last version is the fallback if that fails or is stopped (`notice` on the `done` state), `revisedWith` marks the new one, and `solutionVersions` against a verdict's `versions` tells which solutions changed after it. The run also keeps its confirmed interpretation (`interpretation`: the body's English plus the Chinese and credit, saved with the body in IndexedDB), which `solution-panel.tsx` shows above the solutions. The judge and every interpretation step use the same wrapper, and `useWakeLock` keeps the screen on while anything runs. The page starts a run with a judge only when the form's automatic cross-check asks for one (`autoCheck` in `SolveSubmission`, passed to `start` with its effort) - Careful's, since 16 October 2026 (the owner's call; the presets left it to a tap from 3 October until then), or Custom's when ticked - Quick leaves it to a tap; that judge is sent once the first wave of solvers is done, and the judge's Stop takes it back; `src/lib/presets.ts` holds the presets - Careful and Quick each as Smart or Expert since 16 October 2026, and China since 17 October 2026, `PRESETS[mode][tier]`, a preset carrying its solvers' variants, readers, reconciler and judge; the run keeps the preset's judge as `crossCheckJudge` (`SavedRun.crossCheckJudge`, DEFAULT_JUDGE when unset), which the answer summary's one tap and `CrossCheckControls` start from - Expert's is Claude Opus, China's MiMo V2.6 Pro); a judge in `JUDGE_FALLBACKS` that fails - not a Stop or a re-generation - is handed on once by `handOverJudgeRef` (the run's `judge` gets `fallbackFrom` and `fallbackNote`, the note the verdict's `notice`); `crossCheck(judge, providers)` sends `/api/judge` over the chosen finished solutions (≥2) - since 14 October 2026 as soon as two are in, without waiting for the solvers still running (`waveRef.judgeTaken` then stops the wave from sending its own judge after, and a restored run re-attaches to a judge already sent at once, not after its solvers) - with the run's body - images, notes, confirmed interpretation - and exposes it as `judgeRun` (`start(providers, body, judge)` can still chain one after the wave); the solutions go as Solution A, B, C, D in picker order, and solvers that returned nothing are listed as `skipped`. Under the verdict, `writeStudy(kind, choice, effort, source)` asks for study notes (`components/solve/study-notes.tsx`) starting from `source` - a solver's finished solution, or `"verdict"`: the verdict with the solutions it graded, in its order - as the page shows them (`runsRef` / `judgeRunRef`), with `stopStudy` / `refineStudy` like the verdict's (a re-generation keeps its source); their job ids go in the saved run (`study` in `lib/run-store.ts`), and `restore()` re-attaches the ones that were sent. Model-written prose - the reading, the verdict, the study notes, the answers to questions - goes through `MathProse`, which keeps it to `READABLE_MEASURE` (about 70 characters a line; `wide` opts out), and the prompts ask for short marked lines: one fact per bullet with a bold lead-in in a reading (`READING_FORMAT`, `DISCREPANCY_LINES`), ✓/✗ points and an Agree / Differ / Decisive reason `comparison` in a verdict (the card shows it first, and each assessment's first point with the rest under More), and in study notes short paragraphs, and each worked formula and result as a displayed `$$...$$` equation, the way a solution has them; the notes are shown the way a solution is (`SolutionArticle` with `measure` and `bare` - its type size, line height and centred equations, at the readable line length). How far the answers line up with each other comes from `hooks/use-align.ts` (since 9 October 2026): once every solver has answered - and again when the answers change and none is running - it sends their final answers to `POST /api/align/:provider` (`DEFAULT_ALIGNER`, DeepSeek at `low`), only when `sentHere` from `use-solve.ts` says this page sent them, and re-attaches by the job id it keeps in localStorage after a reload. The rule-based `shared/answers.ts` it replaced is in git history. Solutions open on the **Solution** view (the working; the **All** view was taken out on 12 October 2026 - `AllView` in `solution-views.tsx` is the History's now); `components/solve/hint-stepper.tsx` ("Try it yourself") reveals a solution step by step from `shared/steps.ts`, which reads the `**Step N - ...**` lines the solve prompt asks for. `components/solve/question-images.tsx` shows the run's pages (`questionImages` from `use-solve.ts`) above the solutions and beside the reading in the review step. `hooks/use-completion-alert.ts` counts solvers in the tab's title and sends a desktop notification when opted in.

- Themes: Classic (default), Slate, Graphite and Unicorn (Gundam-inspired), picked in the header (`theme-switcher.tsx`) and set as `data-theme` on `<html>`. All are light - the owner ruled out a dark theme, so there are no `dark:` variants. Colour, radius and heading font come from the `cs-*` tokens in `styles.css` (`text-cs-ink`, `bg-cs-surface`, `border-cs-line`, `bg-cs-accent`, `rounded-cs`, `font-display`, ...); use those instead of hex values, and a new theme is one `[data-theme]` block plus a `THEMES` entry. Status colours (error, timeout, credit badges) stay fixed hex on purpose. Unicorn adds decoration through the `cs-panel` and `cs-primary` hook classes. Solver cards and solution tabs show `ProviderLogo` (`provider-logo.tsx`): the vendors' official marks, SVG files in `src/assets/providers/` named by `ProviderKey`, taken from `@lobehub/icons-static-svg` (MIT). A new provider needs a file there too - the `Record<ProviderKey, string>` fails the typecheck until it has one (Claude Haiku reuses Claude's mark).
